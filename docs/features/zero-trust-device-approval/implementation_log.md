## Phase 1: Database Schema & Device Tracking (Supabase)

### 1. Database Architecture & Schema definition
We have successfully created the Supabase schema script to define the device tracking table.

- **File Created:** [migration-supabase-devices.sql](file:///C:/vs/servx/supabase/migration-supabase-devices.sql)
- **Table Definition:** `public.user_devices`
- **Columns Configured:**
  - `id`: `UUID` (Primary Key, autogenerated using `gen_random_uuid()`)
  - `user_uuid`: `UUID` (Foreign key pointing to `auth.users(id)` with cascading deletion enabled to ensure clean user purges)
  - `device_fingerprint`: `TEXT` (Stores unique device identifier generated from canvas & browser parameters)
  - `device_name`: `TEXT` (User-facing custom display name)
  - `is_main_device`: `BOOLEAN` (Flags a primary device that receives the authentication approval streams)
  - `status`: `public.device_status_type` ENUM (`'PENDING'`, `'APPROVED'`, `'DENIED'`)
  - `last_ip`: `TEXT` (For geolocation/auditing audits)
  - `last_login`: `TIMESTAMPTZ` (Last synchronization timestamp)
  - `created_at` & `updated_at`: Standard metadata audit fields

### 2. Constraints & Optimization
- **Unique Constraint:** `UNIQUE(user_uuid, device_fingerprint)` is established, guaranteeing that a user cannot register duplicate profiles for the same physical fingerprint, while allowing shared systems (same hardware signature) to coexist across different user profiles.
- **Index Optimization:** Compound index `idx_user_devices_user_fingerprint` created on `(user_uuid, device_fingerprint)` for microsecond lookup latencies during Express middleware validation.
- **Trigger Integrity:** Configured PG trigger `trigger_update_device_timestamp` to automatically manage `updated_at` properties on mutation.

### 3. Row Level Security (RLS) Verification
Enabled PostgreSQL Row Level Security on `public.user_devices` with 3 core policies:
- **`Users can view their own devices`**: Select access is strictly limited to records matching `auth.uid() = user_uuid`.
- **`Users can insert their own devices`**: Insert validations enforce that users can only register devices where they own the association.
- **`Users can update their own devices`**: Relies on `auth.uid()` evaluation to permit local modifications (naming adjustments, self-deauthorizations).

## Phase 2: Device Fingerprinting & Auth Middleware

### 1. Persistent Frontend Device Fingerprinting
We have modified the central API layer of the React client:
- **File Modified:** [apiClient.ts](file:///C:/vs/servx/apps/web/src/lib/apiClient.ts)
- **Mechanism:** Leveraged the pre-existing secure browser fingerprinting utility `getDeviceUUID()` inside a global Axios request interceptor.
- **Interception:** Every outgoing request automatically derives the persistent SHA-256 canvas/metadata device fingerprint and injects it into the custom `x-device-uuid` HTTP header. This ensures transparent, zero-friction transmission on every request, including authentication/sync endpoints, without altering standard components.

### 2. Node.js/Express Auth Interception & Verification
We have upgraded the backend synchronization logic to validate the incoming device signature:
- **File Modified:** [controller.ts](file:///C:/vs/servx/apps/api/src/domains/auth/controller.ts)
- **Zero-Trust Logic Flow:**
  - Extracts the `x-device-uuid` signature header.
  - Queries `public.user_devices` inside Supabase matching `user_uuid` (resolved from JWT) and the fingerprint.
  - **First-Device Auto-Approval:** Performs a head check count of user's registered devices. If this is the user's first device, it auto-registers it as `'APPROVED'` and sets `is_main_device = true` to prevent initial onboarding lockout (bootstrapping).
  - **New Device Pending Registration:** If the database contains existing registered devices but the current signature is unrecognized, it registers the new fingerprint as `'PENDING'` with client metadata parsed from the User-Agent (e.g. "Chrome on Windows", "Safari on macOS") and returns a `403 Forbidden` response with code `device_pending_approval`.
  - **Pending State Check:** If a device is already registered but in `'PENDING'` state, it keeps updating `last_ip`/`last_login` and returns the `403 device_pending_approval`.
  - **Denied State Check:** If a device has been explicitly `'DENIED'`, it blocks access immediately with a 403 `device_denied`.
  - **Approved State Passage:** Approved devices automatically update activity parameters and pass through to synchronize details.

### 3. Real-Time Alert Dispatch (Redis PubSub)
- When a device is blocked under `'PENDING'` status (initial attempt or subsequent retry), the backend retrieves a connection to the unified Redis cluster using `getRedisClient()`.
- Publishes a JSON-serialized event (`login_request`) onto the user-specific channel `device_approvals:${id}`, signaling the user's main/approved devices to prompt them for real-time approval.

## Phase 3: Real-Time Signaling (SSE / WebSockets)

### 1. Dedicated Backend Router Configuration
We have created a brand new, domain-isolated routing layer for device operations:
- **File Created:** [router.ts](file:///C:/vs/servx/apps/api/src/domains/devices/router.ts)
- **Mount Point:** Mounted `/api/devices` globally in [app.ts](file:///C:/vs/servx/apps/api/src/app.ts) inside `registerApiRoutes()`.
- **Paths Mapped:**
  - `GET /api/devices/listen-requests` (SSE stream for approved devices)
  - `GET /api/devices/listen-approval/:fingerprint` (SSE stream for unapproved waiting devices)
  - `POST /api/devices/approve` (Decision action endpoint)

### 2. High-Performance Server-Sent Events (SSE) Signaling
We have implemented real-time communication channels in **[controller.ts](file:///C:/vs/servx/apps/api/src/domains/devices/controller.ts)**:
- **Main Device Stream (`GET /listen-requests`)**:
  - Establishes a persistent, non-buffering `text/event-stream` connection.
  - Clones the central Redis client via `.duplicate()` to subscription mode.
  - Subscribes to `device_approvals:${userId}` and immediately flushes published messages to the browser.
  - Incorporates Nginx compatibility (`X-Accel-Buffering: no`) and a 15-second heartbeat loop to prevent proxy connection cuts.
  - Cleans up subscription listeners, terminates Redis connection, and prevents memory leaks upon client disconnect (`req.on('close')`).
- **New Device Stream (`GET /listen-approval/:fingerprint`)**:
  - Establishes a persistent SSE connection for the pending device.
  - Subscribes to `device_approvals:${userId}` but filters messages inside the stream. If `event === 'device_resolved'` and `device_fingerprint` matches the requested param, it pushes the resolution payload (`device_resolved` event) when the target fingerprint matches. This guarantees absolute containment and prevents information leakage.

### 3. Action Mutation Controller (`POST /api/devices/approve`)
- Allows verified main devices to approve or deny a pending device.
- Asserts that both the device and user context match.
- Performs a direct database update in Supabase (`public.user_devices`), setting the status to `'APPROVED'` or `'DENIED'` (and sets custom display names like "MacBook Pro - Home" upon approval).
- Broadcasts the change to Redis PubSub, which instantly triggers the SSE listeners and releases the waiting new device.
